# このリポジトリの思想

コードを読めば「どうなっているか」は分かる。ここに書くのは「なぜそうしたか」と「これから何を守るか」。

## 1. 軽さは機能である

このブログが配っているものを数えると、こうなる。

| 配っているもの   | 量                         |
| ---------------- | -------------------------- |
| 外部 JS バンドル | **0 ファイル**             |
| インライン JS    | 3 箇所・約 40 行           |
| CSS              | 1 ファイル・71 KB          |
| HTML             | 369 ページ（全て事前生成） |

読者が記事を 1 本読むのに、JavaScript のダウンロードも実行も要らない。これは偶然ではなく、そう選んだ結果として維持している。

インライン JS の 3 箇所は次の通り。増やすなら、これと同じ「無くても記事は読める」という条件を満たすこと。

- `app/components/layout.tsx` — スクロールでヘッダーを退ける
- `app/components/post-detail.tsx` — コードブロックの Copy ボタン
- `app/components/toc.tsx` — 目次の現在地表示

> [!IMPORTANT]
> 判断に迷ったら「外部 JS バンドル 0」を基準にする。この数字が 1 になる変更は、それに見合う理由を説明できるときだけ通す。

### 島を建てない

HonoX は islands architecture を持っているが、`app/islands/` は存在しない。作れば必ず JS が配られる。ブログに動く部品は要らないので使っていない。

## 2. 全部ビルド時に済ませる

実行時に計算しないための仕掛けを積んである。

- **シンタックスハイライト** — Shiki がビルド時に色を付ける。クライアントでハイライタを動かさない
- **全文検索** — Pagefind が静的なインデックスを作る。検索サーバは無い
- **記事の更新日** — git のログから引く。`app/lib/vite-plugin-git-timestamps.ts` が全ファイル分をまとめて 1 回で取る
- **OGP カード** — リンク先のメタ情報をビルド時に取りに行き、HTML に焼き込む

Cloudflare Workers に置いてはいるが、やっているのは静的ファイルの配信だけ。動的な処理は無い。

> [!NOTE]
> ビルドが 2 段階なのは HonoX と外部 CSS の組み合わせによる制約。理由は `vite.config.ts` の冒頭に書いてある。

## 3. 道具は増やさない

2026 年時点で、CSS の道具として Tailwind CSS と daisyUI を使っている。これは JS 界隈の人気ランキング上位そのものであって、乗り換える先が無い。

コンポーネントライブラリ（shadcn/ui、Base UI など）は**使えない**。全てランタイム JS を要求し、多くは React に依存する。このブログは `hono/jsx` なので動かないし、動いたとしても第 1 節が壊れる。

フレームワークの乗り換えも考えていない。React も Svelte も htmx も、目指している先は「サーバーが返す HTML」であり、ここは既にそこに到達している。

新しい道具を入れる前に問うこと。**今ある道具で足りないのか。足りないのは道具か、それとも使い方か。**

## 4. 見た目には根拠を持たせる

一度、全画面を 1 枚のルーズリーフに見立てる全面刷新をやって、丸ごと戻した（#75 → #76）。凝った見た目そのものが悪かったのではなく、**CSS とコンポーネントが密に絡んで、一部だけ戻すことも直すこともできなくなった**のが理由だった。

その反省から、見た目の判断は規則として書き下し、規則に沿っているかで議論できるようにしている。

### 面は 3 種類しかない

| 面     | 意味           | 見た目                     |
| ------ | -------------- | -------------------------- |
| 地     | ページの背景   | `bg-base-200`              |
| 紙     | 読むための面   | 白地・**影なし**           |
| カード | **押せる**もの | 白地・影あり・hover で反応 |

**影があれば押せる。** 押せないものを箱で囲まない。この 1 行が守られていれば、箱の有無そのものが情報になる。

### 余白は黄金比の等比数列

`app/style.css` に φ=1.618 のスケールを定義してある。値は用途に対応させる。

| 用途                 | トークン | rem   |
| -------------------- | -------- | ----- |
| 行内の詰め           | `phi-2`  | 0.382 |
| 要素間               | `phi-3`  | 0.618 |
| カードの内側         | `phi-4`  | 1     |
| 紙の内側・ブロック間 | `phi-5`  | 1.618 |
| 大きな区切り         | `phi-6`  | 2.618 |

「紙はカードより内側が広い」を φ 一段の差で表している。新しく余白を足すときは、この表のどれかを選ぶ。`p-5` のような素の値を書かない。

> [!WARNING]
> 例外は `layout.tsx` の `pt-16` ひとつ。固定ヘッダー（daisyUI の navbar = 4rem）の打ち消しなので、φ に乗せると崩れる。

### 配色は retro をそのまま使う

生成りの地に焦げ茶の文字。地と紙の明度差が 3.3% あり、影を外した紙が地に沈まない。暗いコードブロックとの対比も強い。

自前のテーマは持たない。組み込みのまま使えば daisyUI の更新に乗れるし、差分も小さい。

## 5. 何のためのブログか

Rust の学習記録が中心。109 記事の内訳を数えると性格が出る。

| 要素             | 行数  |
| ---------------- | ----- |
| 箇条書き         | 1,627 |
| 引用             | 397   |
| 見出し           | 450   |
| インラインコード | 784   |
| 太字             | **0** |

公式ドキュメントを引用し、その場で考えたことを箇条書きで足していく形。結論をまとめた記事ではなく、読みながら考えた過程がそのまま残る。

だから優先するのは**長文の可読性**であって、一覧の見栄えやトップページの派手さではない。装飾を足すときは「これは読む助けになるか」で決める。

## 6. 検査は全部 CI に入れる

`bun run verify` が CI と同じものを走らせる。oxlint は全カテゴリを error にしてある。

ただし**記事の文章は CI で見ない**。textlint と typos は devShell に入れてあり、書きながらエディタから使う。文章の言い回しは書き手の判断であって、機械が止めるものではない。

> [!CAUTION]
> `nix fmt` は記事内のコードブロックも整形する。学習記録では「あえてこう書いた」コードがあるので、記事を整形したときは差分を確認すること。

## 7. これから

決めていないこと、直していないこと。

- **トップページ** — プロフィールが 1 枚あるだけで、記事が 1 件も出ない。幅も他ページの半分強（`max-w-md`）。第 4 節の規則にも違反している（押せないのに箱）
- **カテゴリ一覧とタグ一覧の重複** — `category/index.tsx` と `tag/index.tsx` がほぼ同型のまま
- **ダークモード** — retro 一本にしたので今は無い。入れるなら `prefersdark` 付きのテーマを足す
